# 사이트 월 운영 장부 — 운영 적용 전 확인

## 현재 범위

- `/admin/finance/monthly-ledger`의 학생별 링크에서 `/admin/finance/monthly-register`로 이동한다.
- 학생·월 하나에 반별 기간/상태/기준금액/할인/이월/일할 차감과 근거를 기록한다. 셔틀비는 학생 월 단위로 한 번만 합산한다.
- 초안 저장 → 저장본 확정 → 사유를 남겨 재열기 순서다. 매 작업마다 새 버전과 전체 내용의 감사 기록을 같은 거래에 저장한다.
- 관리자 직접 입력 장부이며, 시트 대체 완료나 세 시스템 동기화 완료를 뜻하지 않는다. 확정도 청구서 발행 승인이 아니다.
- 월초/기간/정책 금액을 자동 채우지 않는다. 현재 등록 이력이 있는 반만 입력 가능하며, 현재 수강/휴원 반이 빠지면 확정을 막는다. 과거 월 제외 반도 상태와 0원 근거로 명시한다.
- 금액 공제는 승인 근거의 수동 입력이다. 이월 잔액의 차감·소진 추적, 다음 달 자동 이전, 연간 일정 기반 일할 자동계산은 아직 없다.

## 안전한 기본값

- `MONTHLY_REGISTER_WRITES_ENABLED`는 미설정 또는 `false`가 기본이다. POST는 관리자라도 503으로 차단된다.
- 저장을 허용하려면 아래 검증과 사용자 승인을 먼저 완료한다. 이 작업에서는 환경변수를 설정하지 않았다.
- DB 구조가 없으면 GET은 준비 상태를 확인하라는 오류를 반환한다. 조회 시 테이블을 자동 생성하지 않는다.
- `MonthlyEnrollmentRegister`와 `MonthlyEnrollmentRegisterRevision` 외에는 쓰지 않는다. Enrollment, Payment, 시트, Rallyz, 문자·푸시에 연결하지 않는다.
- 저장 결과가 불확실하면 재시도하지 않고 재조회한다. 버전이 바뀐 오래된 요청은 409로 막아 이중 저장을 방지한다.

## 운영 적용 전 필수 검증

1. 별도 테스트 DB의 정확한 프로젝트/접속 대상 확인. 운영 DB URL을 테스트에 사용하지 않는다.
2. `20260904121549_add_monthly_enrollment_register/migration.sql`을 검토한다. Supabase CLI 설치 지연으로 저장소 기존 Prisma 방식의 SQL을 준비했으며, 실제 DB에 적용하거나 실행 검증하지 않았다.
3. 테스트 DB에 새 두 테이블만 적용한다. 전체 미적용 migration을 운영에 일괄 실행하지 않는다.
4. RLS 활성, PUBLIC/anon/authenticated 권한 없음, 서비스 역할의 감사 이력 UPDATE/DELETE/TRUNCATE 금지를 실제 역할별로 조회/시험한다. Prisma 서버 계정의 최소 권한도 확인한다.
5. 다반·휴원·이월·중간 시작의 초안/확정/재열기 저장·재조회, 동시 두 창 저장, 감사 INSERT 실패 시 전체 롤백을 실제 DB에서 검증한다.
6. 이름이 같은 두 학생, 과거 등록 반, 긴 한글 근거, 응답 중단 후 재조회, 월/학생 변경 중 화면 상태를 테스트 브라우저에서 검증한다.
7. 기존 등록/청구 경로가 수정되지 않았는지, 전체 장부/감사 기록이 백업에 포함되는지, 복구 후 버전·합계가 같은지 검증한다.
8. 운영 적용은 대상 DB·새 테이블·기존 자료 변경 없음·쓰기 잠금 유지라는 미리보기를 사용자에게 승인받은 후 별도 시행한다. 활성화도 제한된 대상의 시험 저장 승인 후 진행한다.

## 아직 필요한 시트 대체 작업

- 시트의 대상 월·반별 기록과 새 장부를 건수/금액/상태 단위로 읽기 전용 대조하고 이관 미리보기 작성.
- 할인 정책·이월 잔액/사용 이력·일할 회차 근거 자동 검증 및 실제 Payment/Invoice의 반별 귀속.
- 학교스포츠클럽 수납·토스 대조·메모·통계·셔틀 등 시트 전용 기능과 백업/복구 동등성 검증.
- 사이트를 최종 기준으로 승격하는 별도 승인 전에는 기존 시트/Rallyz 대조를 유지한다.
